# Olimpiada.al — audit and staging validation

**Source:** phase-3-ux-management
**Working branch:** staging-validation
**Production:** master and published website unchanged.

## Verified and corrected
- Teacher accounts are approved by an Admin and require an explicit classroom assignment.
- Approved teacher is given **member**, not moderator, membership within the assigned class (least privilege).
- Forum tier changes and publishing learning resources restricted to the intended administrative/teacher roles.
- Paid students cannot invoke forum-moderation endpoints through the legacy API gate.
- Subscriber-only library pages use an authenticated API and no publicly readable original PDF URL.
- Staging payment receipts are stored as private files, retrievable only using the staff-authenticated endpoint.
- Staging brand uploads are stored separately from private ID photos and PDFs; production still requires configured Cloudinary.
- Staging email is directed exclusively to Mailpit and does not use the configured outbound Resend API.
- PostgreSQL fresh-schema initialization and legacy-schema-to-head upgrade are both covered by independent PostgreSQL 16 CI jobs.
- The multi-service staging project uses separate Postgres and private-volume storage. Exposed ports bind to 127.0.0.1.

## Important limitations and prerequisites
1. This is an **isolated localhost staging** installation, not an online preview domain. The currently connected Vercel team hosts no Olimpiada project. A persistent online staging environment requires separate backend hosting and storage/DB credentials, never production credentials.
2. The initial historical Alembic revisions assume a pre-existing users table. The fresh-stage bootstrap therefore creates the current metadata and stamps the head. This is allowed **only on a blank, isolated staging DB**. Production migrations must use an independently validated backup + migration and must never be stamped blindly.
3. Avoid importing production PII, payment evidence, or real teacher ID photos into staging. Synthetic dummy credentials are generated at local setup and printed only in CMD.
4. Teacher identity documents need a reviewed retention/deletion policy and a staff access audit before production.
5. Outbound email durability/retries, background worker locking and production rate limits still need an operational review.
6. Website DRM cannot stop device screenshots. The viewer uses private server rendering and deterrent watermarks, not guaranteed anti-capture.
7. Not all historic screens are fully translated. SQ is default and the new homepage/FAQ/support have bilingual support.
8. The Premium 1:1 per-session billing flow from Phase 1 still needs explicit settlement processing before commercialization.
9. No deployment or real subscription/payment operations have been run.
